# Development

The full repo is the plugin (`.claude-plugin/`, `.codex-plugin/`, `bin/`, `hooks/`, `skills/`). The Python package
is `src/kb` (stdlib only, Python 3.9). `templates/data/` holds the files that `kb setup` writes into data repos.

## Tests

- `scripts/test` runs the fast tests in parallel on `/usr/bin/python3` with pytest from `uv` (a few seconds).
- `scripts/test --all` adds the tests marked `slow`. These tests start real git and other processes.
- Before each commit, run `scripts/test --all`.
- To run the tests on another Python, set `KB_TEST_PYTHON` (for example `KB_TEST_PYTHON=3.9 scripts/test`). The value
  is a path, or a version that `uv` finds or installs.
- CI (`.github/workflows/test.yml`) runs `scripts/test --all` on each push to `main` and each pull request. It runs on
  Linux with Python 3.9 and 3.13.
- CI installs gitleaks, so the gitleaks tests also run.
- CI has no macOS job, because macOS runners cost ten times more. For a change to macOS behavior, run
  `scripts/test --all` on a Mac.
- The decide mod (`hooks/decide.tsx`, Claude Code only) has its own tests, and CI does not run them. When you change
  the mod, run `claude plugin validate .` and `claude plugin test .`.

## Verification loop

Before each commit, an agent does these steps in this order. If a step changes code, it starts again at step 1.

1. `/simplify` cleans up the diff.
2. `/code-review` finds correctness bugs in the diff.
3. `scripts/test --all` runs the tests.
4. `/verify` runs the change end to end.

`/verify` uses the recipe in `.claude/skills/verify/`. Its `drive.py` makes a sandbox data repo in the temp folder,
with fake sessions. It runs `kb` commands there, or a headless Claude Code session with this checkout as the plugin.
It never uses your real data repo. The recipe also says when to skip `/verify`.

## Releasing plugin changes

When skills or hooks change, increase `version` in `.claude-plugin/plugin.json` and `.codex-plugin/plugin.json`.
Claude Code and Codex keep a cache of plugins per version. The decide mod is part of the hooks, so the same rule
applies to it. The cached `bin/kb` and `bin/kb-guard` run the code clone, so `kb update` gives users a change to them
or to `src/kb/`. The other scripts in `bin/` run from the cache, so a change to them needs a new version.
