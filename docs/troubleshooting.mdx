# Troubleshooting

## Every sync fails to pull

Symptom: each sync fails with `pull: the remote changed this host's files too; run: kb repair`.

On that machine, run these commands in this order:

```bash
kb repair
kb sync --now --no-summaries
```

`kb repair` does these steps:

1. It fetches.
2. It resets the data clone to its upstream.
3. It clears the fingerprints (`files` in `.kb/sync-state.json`).

The next sync writes all sessions again on top of the remote files. It keeps the summaries that it finds there. It
commits only real changes, and pushes.

`kb repair` drops only the work of this host, and the sync makes it again from the local transcripts. The dropped
commits stay in the data clone as `refs/kb/repair/<time>`.

`kb repair` refuses, and changes nothing, in these conditions:

- A sync runs.
- The data clone is not on the configured branch, has no upstream, or cannot fetch.
- A local-only commit or an uncommitted change touches a file outside the folders of this host.

The usual cause: a person wrote the files of this host from another machine. See
[One writer per host](./sync.mdx#one-writer-per-host).

## `host '<host>' belongs to another machine`

Symptom: another machine already uses this `host` name.

- To give this machine its own name, run `install.sh --host <unique-name>`.
- If this machine is the owner and lost only its id (a new data clone, a deleted `.kb/machine-id`), run
  `install.sh --host <host> --force-host`.

See [One host name per machine](./installation.mdx#one-host-name-per-machine).

## `index not built yet; run: kb reindex`

Symptom: the read commands cannot build the index because `.kb/` is not writable (for example, in a sandbox).

To fix it, run `kb reindex` one time from a normal shell.

## Semantic search uses keywords only

Symptom: `kb find` gives keyword results only.

Run `kb find -v <words…>`. It writes on stderr why the query used keywords only:

- `no vectors yet; run: kb embed`: the feature is on, but this machine has no embedded items.
- `the embedding model is starting`: the server was stopped. It starts in the background, and the next query uses it.
- A timeout after a long idle time: the model was unloaded and loads again (about one second).

`kb embed --status` shows the runtime, the server, the vector counts and the path of the server log.

A sync line that ends with `embed: …` names the problem. The sync itself was successful.

`kb embed` fixes most problems. It installs the missing parts, starts the server and embeds the new items.
