# Pages routine

The pages routine keeps the `pages/` folder of the data repo up to date. It writes these files:

- `pages/projects/<project>.md`: state, decisions, files, errors → fixes, open threads
- `pages/retro/<YYYY-Www>.md`: one retro per closed week

Each bullet links to its source session. These commands read the pages:

- `kb page [name] [--section NAME]` prints a page.
- `kb find` lists the matching pages first.
- `kb status` shows the last run of the pages routine.

## Set it up

Use the `setup` skill, or run this command:

```bash
kb setup routine
```

The command pushes `pages/config.json` and the trigger workflow to the data repo. Then it prints these items:

- The routine to create on claude.ai. It has no schedule and no connectors, because it reads untrusted session text.
- The two repository secrets to set from the API trigger of the routine: `PAGES_ROUTINE_FIRE_URL` and
  `PAGES_ROUTINE_FIRE_TOKEN`.

## How a run works

The pages routine runs on claude.ai with two repos next to each other: your data repo and the retroagent code. It
follows [`scripts/pages-routine.md`](../scripts/pages-routine.md). Code does the steps that need no judgement:

| Step | What it does |
| --- | --- |
| `kb pages start` | Selects the branch and builds the index. |
| `kb pages plan` | Selects what to write, from the sessions and memory files changed since the watermark in `pages/.state.json`. |
| `kb pages digest` | Makes a compact input for the model. |
| `kb pages finish` | Refuses files outside `pages/`, bad front matter, pages that are too large and text that looks like a secret. Dates the bullets and moves old bullets to History (see below). Records the watermark, commits and pushes. If sessions were pushed in the meantime, it rebases over them first. |

## Old and conflicting facts

A fact that was true last month can be wrong this month. Thus each bullet of a project page shows the date that a
session last confirmed it. The date is at the end of its sources: `(a1b2c3d4, memory demo/some-fact · 2026-10-07)`.
`kb pages finish` calculates the date from the index: the start of a session, or the modified time of a memory file.
The model never writes the date.

- **Confirmed:** when a new session states the same fact, the pages routine adds its short id. The date moves
  forward.
- **Contradicted:** when a new session states a different fact, the pages routine writes the new bullet. It moves
  the old bullet to History as `superseded <date> by <short>`. When two memory files disagree, the newer one wins. An
  open thread then asks you to delete the old one.
- **Sessions from another folder:** a session belongs to its own project. It also belongs to each project whose repo
  it changed files in or opened a PR in. This is true for all start folders:
  - your home folder
  - `~/Repositories`
  - a Codex scratch folder
  - the `/home/user` folder of a cloud session

  Each plan compares each project page with these sessions, and plans the sessions that the page does not cite.
  The repo folders of a project come from its own sessions. Thus a `docs/` folder in another repo is not the `docs`
  project.
- **Sessions that continued:** a session can continue after a page cited it, because the page was written while the
  session ran. Each plan finds cited sessions that ended after the page or retro was written. It plans the page again
  with them as `grown`. `kb pages finish` refuses to skip such a page. It also refuses to skip a page that does not
  cite one of its planned sessions.
- **Finished:** each time the pages routine updates a page, it checks each open thread against all sessions since
  the thread date. It does not check only the new sessions. If a page never had this check, the plan selects it one
  time for this review, also with no new sessions. `threads_reviewed` in `pages/.state.json` lists the pages that had
  the check. When a session finished a thread (its PR merged, or the task is done), the pages routine moves it to
  History as `closed <date> by <short>`.
- **Current state, not a log:** "Current state" has one bullet per area, as the area is now. It does not include
  details that change in almost each session: version numbers, test counts, timings. Such a bullet stays true longer,
  because new sessions confirm it and do not contradict it.
- **Not confirmed for a long time:** a bullet moves to History as `unconfirmed since <date>` when its date is older
  than the newest bullet on the same page by more than a limit. The limits are:
  - "Current state": `stale_days_current` (30 days)
  - "Errors seen → fixes": `stale_days` (90 days)
  - "Open threads": `stale_days_threads` (30 days)

  The age counts from the page, not from today. Thus a project that you stopped work on keeps its page. "Key
  decisions" and "Important files" never move to History because of age. Only a contradiction replaces them.

The pages routine deletes nothing. `kb find` still finds History bullets. If the sources of a bullet are not in the
index, the bullet gets no date and never moves. `finish` lists these bullets in `undated`, and the moved bullets in
`moved`.

## When it fires

Routine runs are counted per day. Thus `.github/workflows/pages-trigger.yml` in the data repo decides when to fire the
pages routine. It checks on each push to `main`, and every 2 hours. It fires only when both of these are true:

- `kb pages due` finds pages to write. This check takes about a second and uses no LLM.
- Nothing fired the pages routine in the last `min_hours_between_fires` hours (3).

The commits of the pages routine change only `pages/` and contain `[skip ci]`. Thus they never start it. To fire it
immediately, run the workflow manually with the `force` input.

## First run

Until `main` contains `pages/.state.json`, runs write only to the `claude/pages-bootstrap` branch. Review that branch.
Then merge it to start the normal runs on `main`.

## Suggested changes and whether they worked

Each retro ends with "Suggested changes". These are changes to the environment of your agents: a rule, a check, a
hook or a tool. Each bullet starts with an id, like `[s-1a2b3c]`. The model starts a new suggestion with `[new]`, and
`kb pages finish` gives it its id. `kb pages finish` records the suggestions in `pages/suggestions.json`. When the
same problem returns in a later week, the retro cites the same id. Thus you can see a suggestion that returns many
times.

The pages routine also records the decisions on the suggestions in `pages/decisions.json`. It finds the evidence in
the sessions:

- `applied`: a session made the change.
- `accepted`: you asked for the change in your own words.
- `rejected`: you said no in your own words, or a `feedback` memory file says no.

Each decision cites its source. `kb pages finish` takes the date from that source, so the pages routine cannot invent
a date:

```json
{
  "s-1a2b3c": {"state": "applied", "source": "a1b2c3d4", "note": "guard hook patterns fixed",
               "date": "2026-10-09", "by": "routine"},
  "s-4d5e6f": {"state": "rejected", "note": "not worth a check"}
}
```

Your answers from `kb decide` are decisions too (see [Answer a suggestion](#answer-a-suggestion)). You can also add
or change entries of `pages/decisions.json` manually. An entry whose `by` is not `"routine"` is yours. The pages routine never
changes or removes it, and `finish` refuses a run that tries to.

### Answer a suggestion

A new suggestion has no decision. It waits for your answer. To see the suggestions that wait, run `kb decide`:

```text
$ kb decide
s-1a2b3c  proposed  W41           still happening: 3 sessions in 14 days, last 2026-10-09
    Rules · wait for CI with `gh pr checks --watch` (a1b2c3d4)

1 wait for you. Answer one: kb decide accept|reject <id> [--note TEXT]
$ kb decide accept s-1a2b3c --note "add it to AGENTS.md"
```

- `kb decide accept <id>`: the brief then shows the change in each new session of its repo.
- `kb decide reject <id>`: the next retros do not suggest it again.
- `kb decide later [--days N]`: new sessions stop asking about the waiting suggestions for `N` days (default 1). A new
  suggestion makes them ask again.

Run `kb decide accept` and `kb decide reject` in your own terminal, or press the buttons of the
[decide mod](./commands.mdx#answer-in-claude-code). Without a terminal, the commands refuse to run. In Claude Code, a
`PreToolUse` hook also blocks each agent call to them. Thus an agent in a session cannot answer for you. Session text
can hold instructions from other people, and an accepted suggestion reaches every later session of its repo.

The answer goes to `decisions/<host>/answers.jsonl`, and the next sync pushes it. Only the sync of that machine
writes this file. If you answer again, the newest answer counts. A later decision of the pages routine replaces your
answer only when it has a later date: for example, a session applied the change that you accepted. If `kb repair`
drops an answer that was not pushed, the next sync adds it again from a local copy in `.kb/`.

### Measure a suggestion

`kb suggestions` shows each open suggestion with a verdict. If a suggestion names an error signature (from
`kb stats errors`), `kb suggestions` measures it:

- Not applied:
  - `still happening`: the error occurred in the last 14 days.
  - `not seen in 14 days`.
- Applied on a date:
  - `came back`: sessions after that date still have the error.
  - `fixed`: the error did not occur for 7 days or more since that date.
  - `too early to tell`.

`kb suggestions --all` also lists the fixed and rejected suggestions. The next retros read this list. They do not
suggest a rejected change again. They give a higher rank to a change that came back.

## Memory fixes

Claude Code and Codex load the memory files of a folder into each new session there. A wrong memory file thus
misleads every session. The pages routine reads the memory files of all machines. Thus it sees problems that no single
session sees. Each machine keeps its own memory files, and only that machine changes them. Thus the pages routine never
edits a memory file. It proposes a fix, and you accept or reject it with `kb decide`:

```text
$ kb decide
m-4d5e6f  memory    rewrite memory demo/fix-branch: the branch was pushed as PR #1 that evening (a1b2c3d4)
    --- now
    +++ proposed
    -description: Three uncommitted fixes; commit and PR still need the user's go
    +description: Three fixes, pushed and open as PR #1
$ kb decide accept m-4d5e6f
```

A fix is one of these kinds:

- `delete`: a newer memory file or session says the opposite, or the memory file describes work that is over.
- `rewrite`: part of the memory file is wrong, or its summary line no longer agrees with its text. The new text keeps
  the front matter of the file.
- `move`: a Claude Code memory file about one project is in the folder of another project. The fix moves it, with
  its line in the `MEMORY.md` index of each folder.

Only the machine that owns the host of the memory file lists its fixes. `kb decide accept` changes the memory file
on that machine, and the next sync copies the change to the data repo. `kb decide accept` changes nothing in these
cases:

- The memory file changed after the proposal. The pages routine proposes again if the fix still applies.
- The local file changed after the last sync. Run `kb sync --now --no-summaries`, then answer again.
- The target folder of a move is not on this machine.

The pages routine proposes at most 5 fixes in one run, each with the sessions that show it. It proposes one fix for
each version of a memory file. If you reject a fix, it does not ask again until the memory file changes. `kb pages
finish` refuses a rewrite of a memory file that holds a redacted secret, because a rewrite loses the secret.
The proposals are in `pages/memory-edits.json`.

## Settings

`pages/config.json` in the data repo contains these settings:

- the projects to skip
- the minimum number of sessions for a page
- the batch sizes
- the time zone of the retros
- `stale_days`, `stale_days_current` and `stale_days_threads` (see
  [Old and conflicting facts](#old-and-conflicting-facts))
- `max_current_bullets` (10) and `max_open_threads` (8)

`kb pages finish` refuses a project page with more bullets than these limits in "Current state" or "Open threads".
Thus the pages routine keeps these sections to the current state, and closes finished threads. A local `kb sync`
never changes `pages/`.
