# Commands

Run `kb --help` for the full list, and add `--help` to any command for its flags.

## Search and read

| Command | What it does |
| --- | --- |
| `kb find <words…>` | Ranked pages, memories and sessions, one line each, with a snippet and the best turn. Pages come first. Sessions with the exact phrase rank first, then those with every word, then any word; a `"quoted"` part must match as a phrase. `--role user` (or `assistant`) matches only turns by that role, by keywords only, and hides pages and memories. With [semantic search](#semantic-search) on, it also matches paraphrases and other languages; `--no-embed` turns that off for one query, `-v` says on stderr when it was not used. |
| `kb page [name]` | A project page or weekly retro written by the [pages routine](./pages-routine.mdx). `--section NAME` for one part. |
| `kb memory [name]` | A memory file Claude Code or Codex keeps between sessions. No name: list them. |
| `kb recent` | Latest sessions. |
| `kb summary <id>` | Summary, decisions, outcome, files, PRs and subagents of one session. |
| `kb show <id>` | Only the part of a session you need (`--turn N --around K`, `--grep PATTERN`). |
| `kb stats [report]` | Ready-made analytics: overview, projects, agents, outcomes, tags, daily, subagents, errors. `kb stats errors [--since 7d] [--project P]` lists the tool errors that came back in two or more sessions. |
| `kb suggestions [--all] [--json]` | The changes weekly retros suggested, your decisions on them, and whether the error each one should remove still happens. See [Suggested changes and whether they worked](./pages-routine.mdx#suggested-changes-and-whether-they-worked). |
| `kb hint --event error [--hook]` | A past fix for a failed tool call: reads the hook event JSON on stdin, prints one line or nothing. `--hook` prints the hook output JSON. See [Hints when a command fails](#hints-when-a-command-fails). |
| `kb sql "<SELECT …>" [--width N]` | Read-only SQL on the index (tables: `sessions`, `turns`, `pages`, `memories`). Cells longer than `N` chars (default 80) are cut and end with `…`; `--width 0` never cuts. |

Ids are the 8-character short id shown in lists, or any unique prefix of it or of the full id (4 characters at least).

## Sync and maintenance

| Command | What it does |
| --- | --- |
| `kb sync --now` | Sync local sessions now, commit, push. Add `--no-summaries` to go fast. |
| `kb backfill` | Process every pending session now. `--summaries` writes every missing summary. |
| `kb status` | Last sync, pending sessions, summary backlog, gitleaks, the cloud import (when on) and the pages routine's last run. |
| `kb reindex` | Build the local index again. While a sync runs, it only brings the index up to date. |
| `kb embed` | Turn on [semantic search](#semantic-search) and embed what is new. `--status`, `--stop`, `--off`, `--remove`, `--rebuild`; `--install` only downloads and turns it on (a cloud setup script); `--quiet` imports and embeds what is missing, without output, only when it is on. |
| `kb enable [updates]` | Turn automatic syncs (or daily code updates) on. |
| `kb disable [updates]` | Turn them off. |
| `kb repair` | When every sync fails to pull. See [Troubleshooting](./troubleshooting.mdx). |
| `kb update` | Pull the retroagent code and refresh the plugins. |
| `kb cloud import [--on \| --off]` | Show or switch the import of [cloud sessions](#capture-cloud-sessions) on this machine (one machine only). `kb cloud push \| hook \| install` run in the cloud. |
| `kb setup init \| routine \| cloud \| check` | Set up the data repo, the cloud routine and [cloud environments](#in-cloud-sessions-and-routines) (the `setup` skill drives these). |
| `kb pages start \| plan \| digest \| finish \| due` | Steps of the cloud routine. See [Pages routine](./pages-routine.mdx). |

## Semantic search

Optional. `kb find` matches words with BM25. With semantic search on, it also ranks pages, memories and sessions by
meaning with a local embedding model ([EmbeddingGemma 2](https://huggingface.co/google/embeddinggemma-2)) and merges
both rankings. Then "make the CI cheaper" finds a session about "cutting token spend", and an Italian query finds an
English session. A session counts as a match when its summary or one of your own messages in it (40 characters or
more) is close to the query, so a detail you said in the middle of a session can be found too.

`kb embed` sets it up, once:

- It downloads a pinned [llama.cpp](https://github.com/ggml-org/llama.cpp) build for your platform and the model
  (about 330 MB together) into `~/.cache/retroagent/embed/`, and checks both against a pinned sha256. macOS
  (Apple Silicon and Intel) and Linux (x86-64 and arm64) are supported.
- It starts a `llama-server` on `127.0.0.1` (a free port, an API key only `kb` reads, no network access), embeds
  every session, your messages, every page and memory, and turns the feature on.

You manage nothing after that:

- Each sync embeds what it added or changed, for at most `embed_sync_seconds`. If anything goes wrong it adds a note
  to its log line and still succeeds.
- `kb find` waits at most 150 ms for the model. If the server is not running yet, the query uses BM25 alone and the
  server starts in the background for the next one. `kb find` is never slower than without the feature, and never
  fails because of it.
- The server unloads the model after 5 minutes idle (it uses about 500 MB of RAM while loaded), and any `kb` command
  stops the process after an hour without use.
- Vectors live in `<data clone>/.kb/embeddings.sqlite` (a few MB: each keeps 256 of the model's 768 numbers). Each
  sync also commits this machine's vectors to `vectors/<host>/` in the data repo (about 2 KB per session, in half
  precision), and imports the files other machines committed. So another machine, or a cloud session, gets them
  without running the model. Pages are not committed; every machine embeds them, in seconds.
- Searches stay fast as the KB grows. From 5,000 session and message vectors on, a small sign-bit index
  (`.kb/embeddings.bits`, rebuilt when the vectors change) picks the 3,000 closest candidates first, and only those
  are compared exactly. Measured: about 30 ms at 30,000 vectors and 55 ms at 95,000, where comparing every vector takes
  165 ms and 500 ms.
- `kb update` brings new pinned versions; the next sync downloads them.

`kb embed --status` shows what is installed, running and embedded. `kb embed --off` turns the feature off and keeps
the files; `kb embed --remove` also deletes them. To use an embedding server you run yourself, set `embed_url` (see
[Configuration](./configuration.mdx)).

### In cloud sessions and routines

Claude Code cloud sessions and routines can use semantic search too. The vectors come from git, so a session does not
have to embed your whole history: on a cloud CPU that would take about 17 minutes.

- Your machines need semantic search on (`kb embed`). Each sync then commits their vectors.
- `kb setup cloud` prints what to set on a cloud environment at claude.ai/code:
  - the network: **Custom**, the default list included, plus Hugging Face (the model) and the GitHub release hosts
    (the runtime);
  - a setup script that puts `kb` on the PATH and runs `kb embed --install`. Its files are cached for about 7 days,
    and the downloads take about 10 seconds.
- Start sessions and routines in that environment with both repositories: the retroagent code and your data repo.
- The first `kb find` in a session starts a background `kb embed --quiet`. It imports the committed vectors and
  starts the model. Until it is done, `kb find` uses BM25 alone, usually for a few seconds. The pages routine runs
  `kb embed --quiet` itself at the start.
- A session only reads vectors: it never commits any, because it owns no host.

### Capture cloud sessions

A cloud container is deleted after its session, with its transcript. The setup script from `kb setup cloud` also
runs `kb cloud install`: it adds a `Stop` and a `SessionEnd` hook to `~/.claude/settings.json` in the container.

- After each answer, the hook starts `kb cloud push` in the background. It slims and redacts the transcript and its
  subagents, like a raw copy, and commits them as `inbox/claude/<encoded cwd>/<id>.jsonl.gz` on the branch of the data
  clone: the session's own `claude/…` branch. It never pushes to `main`, and it does not touch the working tree.
- On one machine, run `kb cloud import --on`. Each sync of that machine then fetches every branch, copies the inbox
  files into `.kb/cloud/`, and processes them as the sessions of host `cloud`: markdown, raw copy, summary, catalog
  and vectors, as for its own sessions. `kb find`, `kb page` and the pages routine see them like any other session.
- A copy replaces the imported file only when it extends it, so an older copy on a kept branch never wins. A shorter
  copy with another history is reported in the sync line, and its branches stay.
- That machine owns `sessions/cloud` (the host marker, see [Sync](./sync.mdx#one-writer-per-host)). A second machine
  with the import on writes nothing for it and says so in its sync line.
- After a clean push, the sync deletes each branch whose only change from `main` is `inbox/`. A branch with other
  commits stays; do not merge it as it is, or `inbox/` reaches `main`. If the session goes on, its next push starts
  the branch again from `main`.
- One-prompt headless runs, such as the pages routine, are not pushed (the sync skips them too), and nothing is pushed
  on `main` or on the routine's bootstrap branch. Errors go to `.kb/cloud.log` in the cloud data clone.
- A session's project comes from its working directory. A cloud session that starts with more than one repository
  works in `/home/user`, so its project is `user`.

## Hints when a command fails

Optional, off by default. Turn it on with `"hints": true` in the [config](./configuration.mdx). When a tool call
fails in Claude Code, the `PostToolUseFailure` hook (`bin/kb-hint`) runs `kb hint --event error`. It can add one line
to the agent's context:

```
retroagent: seen before → <problem → fix> (kb summary <short> · <date>)
```

The line is a bullet from the "Errors seen → fixes" section of the current project's page, with the session it came
from and the date a session last confirmed it (see
[Old and conflicting facts](./pages-routine.mdx#old-and-conflicting-facts)). A bullet that the page's age rule calls
stale (`stale_days` in `pages/config.json`) is never shown. The project comes from the working directory, as for sessions. Most failures get no hint, because a wrong hint
costs more than a missing one:

1. The first 200 characters of the error must contain an error word (`error`, `failed`, `not found`, `denied`, …). An
   error with no message, such as `grep` exit 1, or plain command output with exit code 1, gets no hint.
2. A permission, auto mode classifier, sandbox or safety denial never gets a hint, and a bullet about one is never
   shown.
3. When the embedding server of [semantic search](#semantic-search) already runs, the bullet closest in meaning, at
   least `hint_semantic_min` (cosine). The hint never starts the server. The bullet vectors are kept in
   `.kb/hints/vectors/`, so a hint embeds only the error.
4. Else, the bullet whose problem side (the text before `→`) shares at least `hint_keyword_min` words with the error.
   Paths, numbers, ids, quoted values and common words do not count.

A session gets each bullet once. When its best bullet was shown already, it gets nothing. The hook exits 0 on every
problem and prints nothing; when hints are off it exits before Python starts. Each hint shown is logged to
`.kb/hints/log.jsonl` in the data clone (local, never committed) with the session, the bullet, its date, the score
and the rule.

Codex has no event for a failed tool call, and its `PostToolUse` shell response has no exit code, so Codex gets no
hints yet. `kb hint` still reads a Codex `PostToolUse` event whose response starts with `Exit code: N`.

`scripts/hint-replay` replays the hint rules on the tool errors of your data clone (read-only) and prints how many
hints each rule would show. `--semantic --start` also runs the semantic rule, `--show N` prints examples.

## Read-only by design

The read commands open the local index read-only. They work in a sandbox where `.kb/` cannot be written, and they
never wait for a running sync.

Only a missing or outdated index must be built, which needs write access. If it cannot be built, they print
`index not built yet; run: kb reindex` and exit 2. Other errors print one line, `kb: <message>`, and exit 2.
